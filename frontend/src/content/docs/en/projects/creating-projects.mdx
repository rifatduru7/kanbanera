## What a project should represent

A project should represent a real delivery boundary. It needs a clear owner, a coherent workflow, and a task set that belongs together.

Avoid using one project for every possible initiative. Use projects to create clarity, not a dumping ground.

## Fields you set at creation time

When you create a project, the current experience lets you define:

- name
- description
- color
- template

The template is the fastest way to start with a sensible structure when the team is new to the workspace.

## Naming conventions

Choose names that answer one question immediately: “What work lives here?”

Good names are:

- Launch Website Q2
- Customer Onboarding Revamp
- Internal Ops Automation

Less useful names are generic labels like “Tasks” or “General”.

## Project color and recognition

Project color is a small decision with real UI impact. It helps cards, highlights, and selection states feel recognizable across views.

Use color as a recognition aid, not as the only source of meaning.

## Grid and list management

The Projects screen supports visual browsing and simpler scanning. Use:

- grid view for recognition and overview
- list-style density when comparing several projects quickly

You can also search by project name or description and control whether archived items are shown.

## Archiving vs deleting

Archiving is for inactive work that may still need historical access.

Deleting is permanent and should be reserved for mistakes, duplicates, or intentionally removed workspaces.

## Next steps after creation

Once the project exists:

1. Review columns in Board.
2. Invite members.
3. Create the first real tasks.
4. Open Calendar or Gantt once dates matter.
